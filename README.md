## Стек

- **Контракт API:** TypeSpec → OpenAPI → клиентский SDK (`@hey-api/openapi-ts`)
- **Бэкенд:** Node.js 24, TypeScript, Fastify 5, хранение данных в памяти процесса
  - Тесты: Vitest
- **Фронтенд:** React 19, TypeScript, Vite
  - UI: Mantine 9 (`@mantine/core`, `@mantine/dates`, `@mantine/form`, `@mantine/notifications`)
  - Запросы к API: сгенерированный SDK + TanStack Query 5
  - Роутинг: React Router
  - Даты: dayjs
  - Тесты: Vitest + Testing Library, Playwright
- **Деплой:** Docker, [Render](https://render.com/)

## Установка

Всё окружение описано в `mise.toml`: версии инструментов, переменные окружения, задачи и фоновые dev-серверы.
Нужен [mise](https://mise.jdx.dev/getting-started.html).

```bash
git clone https://github.com/sergdenisov/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install   # инструменты, а через хук postinstall — npm-зависимости и git-хуки
```

### Агенты

Скиллы, которыми сделан проект (`/wayfinder`, `/to-spec`, `/to-tickets`, `/implement-spec`, `/tdd`, `/code-review` и
другие), — плагин [`mattpocock-skills`](https://github.com/mattpocock/skills). `.claude/settings.json` включает его
вместе с плагином Render, и Claude Code предлагает поставить оба при первом открытии проекта. Вручную:

```text
/plugin install mattpocock-skills@claude-plugins-official
/reload-plugins
```

Настройки скиллов для этого репозитория (трекер задач, метки, документы домена) лежат в `docs/agents/`, правила для
агентов — в `AGENTS.md`.

### Разработка

```bash
mise run dev                  # бэкенд (http://127.0.0.1:3000) и фронтенд (http://127.0.0.1:5173) в фоне
mise daemons status           # состояние dev-серверов
mise daemons logs backend     # логи (backend или frontend)
mise daemons restart frontend # перезапуск
mise daemons stop             # остановить всё

mise run check       # все проверки, как в CI, включая браузерные сценарии
mise run check:e2e   # только браузерные сценарии (Playwright) на собранном приложении
mise run fix         # безопасные автоисправления (форматирование и т. п.)
mise run check:docker # сборка Docker-образа и проверка контейнера (нужен запущенный Docker)
mise run build       # сборка бэкенда и фронтенда
mise run start       # сборка и запуск приложения: бэкенд отдаёт API и фронтенд, как в Docker-образе
mise tasks           # все задачи
```

Dev-серверы работают как daemons mise под управлением [pitchfork](https://pitchfork.jdx.dev/), поэтому их можно
запускать, останавливать и смотреть их состояние из любого терминала. Порты задаются в `mise.toml`
(`BACKEND_PORT`, `FRONTEND_PORT`).

### Браузерные сценарии

`mise run check:e2e` собирает бэкенд и фронтенд и прогоняет сценарии Playwright из `frontend/e2e/` в Chromium:
Owner создаёт тип события, Guest записывается на первый свободный слот, а Owner видит её среди предстоящих
записей; две вкладки выбирают один слот, и вторая получает сообщение о конфликте. Сценарии работают с настоящим
сервером без подмены ответов: Playwright сам запускает собранный бэкенд с флагом `--validate-responses` (ответ не по
контракту превращается в ошибку 500), который отдаёт и собранный фронтенд, как в Docker-образе. Порт отдельный,
поэтому dev-серверы можно не останавливать. Задача входит в `mise run check`, но не в хук pre-push. Chromium ставит
`mise run install`. Если сценарий упал, отчёт лежит в `frontend/playwright-report/`
(`npx playwright show-report` в `frontend`), а в CI он загружается артефактом `playwright-report`.

### Контракт API

Репозиторий состоит из трёх npm-пакетов: `spec` (контракт на TypeSpec), `backend` и `frontend`. API описывается
сначала в `spec/main.tsp`, а код по нему генерируется:

```text
spec/main.tsp ── tsp compile ──> spec/openapi.yaml (OpenAPI 3.0.0)
                                  ├── openapi-ts ──> frontend/src/api/generated/  SDK: клиент fetch + TanStack Query
                                  └── openapi-ts ──> backend/src/api/generated/   типы обработчиков + копия контракта
```

```bash
mise run generate        # пересобрать OpenAPI, SDK и типы бэкенда после правки spec/main.tsp
mise run check:contract  # проверить, что закоммиченное сгенерированное совпадает с контрактом
```

Генератор `@hey-api/openapi-ts` и его настройки (`spec/openapi-ts.config.ts`) живут в пакете `spec` вместе с
TypeScript 6: генератору нужен API компилятора TypeScript, которого нет в TypeScript 7 бэкенда и фронтенда.
Сгенерированные файлы коммитятся и руками не правятся (ADR 0003). Бэкенд отдаёт API под `/api`, а Vite в dev
проксирует `/api` на бэкенд. API-тесты запускают приложение с `validateResponses`: ответ, которого нет
в контракте, превращается в ошибку 500.

## Агент в GitHub

В GitHub агентом работает [OpenCode](https://opencode.ai/docs/github/): событие в репозитории запускает его в GitHub
Actions, а ответ появляется комментарием от имени приложения
[`opencode-agent`](https://github.com/apps/opencode-agent). Приложение установлено на репозиторий, ключ модели лежит в
секрете `OPENCODE_API_KEY` (Settings → Secrets and variables → Actions). Это стандартная интеграция OpenCode, другой
агент не настраивался.

сессия читает их перед работой.

### Автотриаж новых обращений

`opencode-triage.yml` разбирает новое обращение сразу после создания. Агент по скиллу `triage` смотрит, что уже умеет
приложение, ставит одну метку категории (`bug` или `enhancement`) и одну метку состояния: `needs-info`, если данных не
хватает, иначе `needs-triage`. В комментарии он даёт рекомендацию или, для `needs-info`, конкретные вопросы шаблоном
Triage Notes. Код агент не меняет, issue не закрывает и `ready-for-agent` не ставит: взять задачу в работу решает
человек.

Задание отсеивает всё лишнее до вызова модели: обращение от бота, от автора без прав (`OWNER`, `MEMBER`,
`COLLABORATOR` по `author_association`) и с любой меткой состояния из `docs/agents/triage-labels.md` (`needs-triage`,
`needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). Спецификации и тикеты `to-spec`/`to-tickets` приходят от
`opencode-agent[bot]` уже с `ready-for-agent`, поэтому пропускаются. Задание ограничено 15 минутами, `concurrency` —
по номеру issue.

Этот воркфлоу написал агент по [#18](https://github.com/sergdenisov/ai-for-developers-project-387/issues/18), но
запушить его не смог: GitHub не даёт GitHub App менять `.github/workflows/` без права `workflows`, а у приложения
`opencode-agent` его нет, и выдать его может только владелец приложения. Поэтому изменения воркфлоу агент готовит, а
пушит человек или локальный агент; здесь его правки восстановлены из лога прогона.

### Скиллы из комментария

Скилл запускается командой с его именем. Ссылку на прогон агент оставляет в ответном комментарии, а все прогоны и лог
сессии видны в [Actions → opencode](https://github.com/sergdenisov/ai-for-developers-project-387/actions?query=workflow%3Aopencode).
Примеры для этого репозитория:

```text
/oc запусти скилл to-spec по обсуждению этого issue
/oc запусти скилл to-tickets по спецификации #12
/oc запусти скилл implement-spec по спецификации #12
```

- **`to-spec`** собирает спецификацию из обсуждения и публикует её новым issue с меткой `ready-for-agent`. Агент
  отвечает комментарием со ссылкой на созданный issue.
- **`to-tickets`** режет спецификацию на вертикальные тикеты и заводит по issue на каждый, связывая блокировки
  нативными зависимостями GitHub. Тикеты получают метку `ready-for-agent`, родительский issue не меняется. Если
  скилл запущен по существующему issue, каждый тикет становится подзадачей (sub-issue) этого issue. Агент отвечает
  комментарием со списком заведённых тикетов.
- **`implement-spec`** проходит граф тикетов на интеграционной ветке и открывает PR: черновик после первого слияния,
  затем готовый к ревью. PR закрывает спецификацию и её тикеты, а агент отвечает комментарием со ссылкой на него.

Issues и PR, которые заводят скиллы, подписаны `opencode-agent[bot]`: `gh` работает токеном GitHub App, как и сам
агент (см. «Настройки `opencode.yml`»). Поэтому на PR агента сам запускается `check.yml`.
`implement-spec` работает долго: на одно обсуждение запускается один агент, остальные команды ждут в очереди, а
агент ограничен 55 минутами внутри часового задания (см. «Настройки `opencode.yml`»).

### Настройки `opencode.yml`

- **Команды (`mentions`):** набор по умолчанию, `/oc,/opencode`, записан в воркфлоу явно (`MENTIONS`). Те же команды проверяет
  условие `if` задания `gate`, поэтому при смене набора меняются оба места.
- **Публикация сессий (`share`):** выключена (`SHARE: false`). Репозиторий открытый, а сессия содержит контекст задачи.
  OpenCode 1.19 этот параметр игнорирует, потому что публикацию сессий в нём убрали, но решение записано в воркфлоу
  на случай, если она вернётся. Ход работы смотрите в логе прогона в Actions.
- **Модель заголовков:** заголовок сессии OpenCode генерирует отдельным агентом `title`, по умолчанию маленькой моделью
  `gpt-5.4-nano`, а в нашем рабочем пространстве Zen она недоступна. `opencode.json` в корне задаёт агенту `title` ту
  же `opencode/deepseek-v4.1-flash`, поэтому весь прогон оплачивается одной моделью. Устаревший ключ `small_model`
  делает то же, но `agent.title.model` имеет приоритет над ним.
- **Без вопросов о правах:** на раннере некому ответить на запрос разрешения, и такой запрос висит до тайм-аута. Так
  уже было: агент захотел записать файл в `/tmp`, OpenCode спросил разрешение `external_directory`, и прогон завис.
  Поэтому воркфлоу через `OPENCODE_PERMISSION` заранее отвечает на всё, о чём OpenCode 1.19 по умолчанию спрашивает:
  папки вне рабочей копии разрешены (shell и так до них достаёт), а зацикливание (`doom_loop`) и чтение `.env`
  запрещены. Локальный OpenCode эта переменная не затрагивает.
- **Кто может вызвать:** только владелец, участники организации и коллабораторы (`author_association`), и не бот, чтобы
  агент не отвечал сам себе. Сам OpenCode дополнительно требует у автора права `write` или `admin`. Остальные
  комментарии пропускаются без вызова модели.
- **PR из форков:** задание `gate` работает без секретов и не пускает дальше PR, чья ветка лежит в форке: агент мог бы
  запустить код такого PR рядом с ключом модели. `pull_request_target` не используется.
- **Права:** у задания с агентом `contents: read` и `id-token: write`, токен Actions ничего не пишет. По OIDC-токену
  OpenCode получает токен GitHub App и через него комментирует и пушит; checkout идёт с `persist-credentials: false`.
  Команда `gh` тоже работает от имени приложения: шаг перед агентом так же обменивает OIDC-токен на отдельный токен
  App и передаёт его в `GH_TOKEN`, а последний шаг отзывает его. Права этого токена — права приложения
  `opencode-agent`, поэтому скиллы `to-spec`, `to-tickets` и `implement-spec` сами заводят issues с метками,
  подзадачами и блокировками и открывают PR, всё от имени `opencode-agent[bot]`.
- **CI на PR агента:** PR, открытый токеном Actions (`GITHUB_TOKEN`), не запускает другие воркфлоу, а PR и коммиты от
  GitHub App запускают. Поэтому на PR агента `check.yml` стартует сам, как на PR человека.
- **Модель:** `deepseek-v4.1-flash` — самая новая модель DeepSeek в Zen: $0.30 за 1M входных токенов и $1.20 за 1M
  выходных, дешевле DeepSeek V4 Pro ($1.74/$3.48) и Claude Sonnet ($2/$10). Цены — на [странице Zen](https://opencode.ai/docs/zen/).
- **Остановка:** агент останавливается через 55 минут (`timeout` в шаге), задание с ним — через 60, `gate` — через 5.
  `concurrency` по номеру issue или PR запускает одного агента на обсуждение, а следующие команды ждут в очереди
  (`queue: max`). Текущий прогон
  останавливает Cancel workflow, будущие — Disable workflow на странице воркфлоу. Уже отправленный запрос провайдер
  может доработать по своим правилам; при необходимости отзовите ключ в
  [консоли OpenCode](https://opencode.ai/auth). Бюджет задаётся там же.

### Что агент получает на раннере

Раннер начинает с чистого окружения, поэтому воркфлоу готовит то же, что есть локально:

- **Правила и настройки** приходят вместе с кодом: `AGENTS.md`, трекер, метки и документы домена в `docs/agents/`.
  Трекер — GitHub Issues этого репозитория, команда `gh` работает с ним через `GH_TOKEN` от имени приложения.
- **Скиллы** локально приходят из плагина `mattpocock-skills` (см. «Агенты»), а не из репозитория. Воркфлоу скачивает
  ту же версию 1.3.1, закреплённую по коммиту, и ставит все скиллы плагина как глобальные скиллы OpenCode
  (`~/.config/opencode/skills`), вне рабочей копии. Шаг падает, если среди них нет `to-spec`, `to-tickets` или
  `implement-spec`. При обновлении плагина обновите `SKILLS_SHA` в воркфлоу.
- **Инструменты** из `mise.toml` ставит `jdx/mise-action`. npm-зависимости агент ставит сам командой
  `mise run install` перед проверками.

OpenCode закреплён на версии 1.19.6. Воркфлоу не использует action `anomalyco/opencode/github`, а повторяет его шаги:
скачивает архив релиза, сверяет его SHA-256 и запускает `opencode github run`. Action узнавал последнюю версию
анонимным запросом к GitHub API, и на общих раннерах этот запрос падал раньше, чем стартовал агент. Новую версию
OpenCode ставим вручную: обновите `OPENCODE_VERSION` и `OPENCODE_SHA256` (дайджест `opencode-linux-x64.tar.gz` на
странице релиза).

### Авторевью

`opencode-review.yml` проверяет каждый PR в отдельной сессии, не той, что писала код. Ревьюер — обычный OpenCode CLI
(`opencode run`), а не `opencode github run`: тот проверяет права отправителя события, а у приложения, которое открывает
PR агента, это `none`, и ревью таких PR остановилось бы. Поэтому доверенного автора и ветку проверяет сам воркфлоу, до
вызова модели: ветка этого репозитория (PR из форка ключ модели не получает), не черновик, автор — `OWNER`, `MEMBER`,
`COLLABORATOR` или `opencode-agent[bot]`. Фильтра по типу Bot нет, иначе PR агента остались бы без ревью; PR
dependabot и release-please в список не входят.

- **Критерии:** [`REVIEW.md`](REVIEW.md) — что ломает календарь (занятый слот снова доступен, время не в зоне Owner,
  ответ вне контракта и т. д.), глубина проверки по риску и формат замечания: файл, строка, условие, последствие.
  Воркфлоу явно прикладывает этот файл к запросу (`--file`), причём из базовой ветки, а не из PR: PR не может ослабить
  критерии собственного ревью.
- **Что читает:** ревьюер работает в checkout базовой ветки, поэтому `opencode.json`, плагины и `AGENTS.md` тоже из
  неё: изменённые в PR, они не выполнились бы рядом с ключом модели. Сам PR задание заранее собирает в
  `review-input/` как данные: описание и комментарии (прежние ревью тоже), diff, изменённые файлы в версии head,
  связанные issues (обращение, спецификацию, тикеты, согласование) и состояние CI. Перед этим оно до 15 минут ждёт
  `check.yml` на head SHA.
- **Права:** токен задания только на чтение (`contents`, `issues`, `pull-requests`, `actions`, `checks`, `statuses`),
  OIDC не нужен, а в окружение модели токен не передаётся вовсе. Модели запрещены shell (иначе она могла бы напечатать
  окружение с ключом), правка файлов, веб и чтение вне рабочей папки (`OPENCODE_PERMISSION`). Комментарий публикует
  отдельное задание `publish` без модели с `pull-requests: write`.
- **Остановка:** тайм-аут 45 минут: до 15 на ожидание CI и до 20 на модель. `concurrency` по номеру PR отменяет
  ревью устаревшего head при новом push. Если ревью не получилось, `publish` пишет причину (`infra`, `timeout`,
  `agent_failed`) и SHA.
- **Исправления** ревью не запускает: человек разбирает замечания и передаёт подтверждённые агенту командой `/oc` в PR.
  Так ревью и правки не уходят в бесконечный цикл.

Воркфлоу в `.github/workflows/` пишет локальный агент: у приложения `opencode-agent` нет права `workflows`, и его push
такого файла GitHub отклоняет (см. «Автотриаж новых обращений»).

### Предел запусков на PR

На один PR агент запускается не больше трёх раз. Задание `gate` в `opencode.yml` считает попытки до вызова модели, по
истории Actions: каждый прогон, где задание агента не было пропущено, в том числе отменённый, упавший по тайм-ауту и
каждая попытка Re-run. Прогоны PR узнаются по заголовку `opencode PR #N` (`run-name`). Если история недоступна,
`gate` падает и агента не пускает. Бюджет считается с момента, когда появился `run-name`: прогоны PR, открытых раньше,
под этот заголовок не попадают и в счёт не идут. Эту историю токен агента
переписать не может; комментарии — только отчёт. Четвёртая команда `/oc` в PR завершается без вызова модели. Новый PR
получает новый бюджет, а команды в issue бюджет не тратят. Ограничение держится, пока цела история Actions и
конфигурация воркфлоу: администратор репозитория может их изменить.

Когда агент не запустился или не закончил, задание `report` без модели пишет в issue или PR «нужен человек», причину,
SHA и ссылку на логи:

| Причина           | Когда                                                                                  |
| ----------------- | -------------------------------------------------------------------------------------- |
| `limit_exhausted` | бюджет PR исчерпан, модель не вызывалась                                              |
| `infra`           | сбой подготовки: упал `gate`, установка инструментов, токен приложения, нет ключа `OPENCODE_API_KEY` |
| `timeout`         | агент не уложился в 55 минут (`timeout` в шаге) или задание — в 60                     |
| `agent_failed`    | агент завершился ошибкой или прогон отменён; уточните по логу                          |

### Проверка версии PR перед мержем

Задание `e2e-head` в `check.yml` запускает браузерные сценарии на точном head SHA PR, а не на временном merge-коммите,
и с `E2E_TRACE=on` сохраняет trace и скриншот каждого теста, в том числе успешного. Артефакт `e2e-head-<SHA>` содержит
`result.txt` (проверенный `git rev-parse HEAD`, head PR, результат, ссылку на прогон), HTML-отчёт Playwright и trace.
Перед мержем человек сверяет SHA артефакта с текущим head PR и открывает отчёт. После нового push старый артефакт
остаётся свидетельством прежней версии, поэтому проверку повторяют.

### Шаблон PR

`.github/pull_request_template.md` задаёт разделы: связи (обращение, спецификация, тикеты, согласование, `Closes #N`),
что сделано, проверки (команды, ссылки на прогоны, проверенный SHA), риск (что может сломаться, кого затронет, глубина
проверки по последствиям ошибки) и откат (как отменить в Git, чем проверить восстановление, достаточно ли отмены кода для
данных). Агент заполняет его в своих PR (`AGENTS.md`).

### Аудит страниц

`lighthouse-audit.yml` раз в сутки проверяет работающее приложение Lighthouse и превращает находки в задачи. Время —
06:17 по Москве (`timezone: Europe/Moscow`). GitHub может задержать или пропустить запуск по расписанию, а в
публичном репозитории отключает расписание после 60 дней без активности. Тот же сценарий запускается вручную: Actions
→ lighthouse-audit → Run workflow из `main`.

1. **`collect`** без модели и секретов будит приложение (бесплатный Render засыпает, до 4 минут ожидания), запускает
   Lighthouse 13.6.0 на `/` и `/book` по адресу из переменной репозитория `APP_URL` и сохраняет HTML- и JSON-отчёты в
   артефакт `lighthouse-report` на 30 дней. Отчёты лежат вне рабочей копии и в коммиты не попадают. Находка — аудит,
   который влияет на оценку категории (вес больше 0) и получил меньше 0.9, а для метрик производительности (FCP, LCP,
   TBT, Speed Index, CLS) — меньше 0.5, «красную» зону: на бесплатном Render они колеблются от прогона к прогону. Ключ
   находки — id аудита Lighthouse, страницы, где она проявилась, собраны в одну находку, а из селекторов элементов
   вырезаны id, которые Mantine генерирует при каждой загрузке. `/admin` не проверяется: там имена и почты гостей. Если
   приложение не ответило, статус прогона `no_data`: это отсутствие данных, а не признак, что находки исправлены.
2. **`analyze`**: агент OpenCode читает сводку отчёта и issues прежних аудитов и отвечает решением в JSON: для каждой
   находки — создать issue, дополнить открытый новыми сведениями, создать issue заново, если находка вернулась после
   закрытого (со ссылкой на него), или ничего не делать, если она уже ведётся без изменений. Инструкция — в `PROMPT`,
   комментария у расписания нет. Модель работает без shell и без токена GitHub: отчёт цитирует страницы, а на них текст,
   который может написать кто угодно (названия типов событий, админка открыта, ADR 0001); с shell такой текст мог бы
   заставить модель вывести свой ключ в issue.
3. **`apply`** без модели, с `issues: write`, исполняет решение после проверки: находка должна быть в отчёте этого
   прогона, а второй открытый issue по тому же ключу код не создаст, что бы ни решил агент (метка `lighthouse` и
   маркер `<!-- lighthouse-finding: KEY -->` в теле). Каждый issue описывает проблему, доказательства, предлагаемое
   действие, проверенное приложение и ссылку на прогон. Итог прогона (оценки, находки, решения, ссылка) комментарием
   уходит в журнал аудита — issue с меткой `lighthouse-log`, который хранит результат и после того, как истекут
   артефакты.

Права: `collect` — никаких, `analyze` — `contents: read` и `issues: read` (читает прежние issues до запуска модели),
`apply` — `issues: write`. OIDC и токен GitHub App не нужны: агент ничего не пушит и не открывает PR, а issues создаёт
задание `apply` токеном Actions. Такие issues не запускают другие воркфлоу, в том числе автотриаж. Новая задача —
входящее обращение: брать ли её в работу, решает человек, дальше — обычная цепочка спецификации и тикетов. Тайм-ауты:
15, 35 и 5 минут (модели — до 25 и ещё 5 на повторный ход: OpenCode Zen иногда отвечает на шаг минутами); `concurrency`
держит один аудит за раз.

## Выводы о работе агента в GitHub

Мои выводы после четырёх заданий с агентом OpenCode в GitHub Actions: установка, работа с issue и триажем, путь от
issue до pull request и ревью, регулярный аудит. Факты — в разделах выше и в истории PR.

### Что работает

- **Обсуждение в issue заменяет сессию агента.** Триаж, вопросы агента, мои ответы, спецификация и тикеты остались в
  #13–#16. `implement-spec` в новом прогоне прочитал их по ссылкам, и заметка «О чём звонок» прошла путь от обращения
  до релиза 0.3.0 без локальной сессии.
- **Независимое авторевью находит настоящие проблемы.** На PR с самим воркфлоу ревью (#23) оно нашло 14 замечаний, три
  из них — дыры в безопасности самого ревьюера; на аудите (#32) — баг в защите от дублей. Самыми ценными оказались
  замечания про права и секреты, а не про код календаря.
- **Код надёжнее инструкции.** Там, где ошибка дорогая, правило проверяет код без модели: доверенного автора и форк — в
  `gate`, бюджет запусков — по истории Actions, дубли задач — по маркеру находки в `apply`. Модель решает, код
  проверяет и исполняет.

### Что потребовало уточнений

- **Права приложения.** У `opencode-agent` нет права `workflows`: агент написал воркфлоу автотриажа, но запушить не
  смог, поэтому все воркфлоу вносил локальный агент. Токен Actions, наоборот, не запускает CI на созданных им PR,
  поэтому `gh` агента я перевёл на токен приложения.
- **Агент на раннере не может задать вопрос.** Запрос разрешения на запись в `/tmp` повесил прогон на 13 минут; теперь
  `OPENCODE_PERMISSION` заранее отвечает на всё, о чём OpenCode спрашивает по умолчанию.
- **Модель.** Sonnet оказался дорогим, я перешёл на DeepSeek V4.1 Flash. Её рассуждения на большом контексте съедали
  весь лимит вывода OpenCode в 32 000 токенов, и ревью выходило пустым. Помогли `--variant low`, повторный ход той же
  сессии и правило «ревью — только текст шага, закончившегося `stop`». Модель заголовков `gpt-5.4-nano` оказалась
  выключена в Zen, я задал свою в `opencode.json`.
- **Action OpenCode.** Он узнаёт последнюю версию анонимным запросом к GitHub API, и на общих раннерах этот запрос
  падал. Я заменил action его же шагами с закреплённой версией, проверенной по SHA-256.
- **Где модели нельзя давать shell.** Ревьюер сначала работал в checkout PR рядом с ключом модели и мог прочитать
  окружение, а аудит читает страницы, на которые может написать кто угодно. В обоих случаях модель теперь без shell и
  без токена, а пишет в GitHub задание без модели.
- **Мелочи, которые ломают процесс.** Заголовок PR, который OpenCode ставит сам, не по Conventional Commits, а
  release-please берёт строку журнала из него. `gh … view --comments` отдаёт только комментарии, и ревьюер видел
  «пустое описание». 503 от github.com в проверке ссылок и тесты Хекслета, которые не запускаются на release-PR,
  блокировали мерж после включения защиты `main`.

### Что я изменил в постановке задач

- В комментарии `/oc` пишу, что можно менять и чего нельзя («код не меняй», «если объём меняется, спроси здесь»),
  какие проверки запустить и в каком формате коммит. Без этого агент делает больше, чем нужно, или меньше.
- Шаги с согласованием человеком делю на два запуска: `to-tickets` сначала показывает разбивку, а публикует после моего
  ответа.
- Не верю сообщению «тесты прошли»: смотрю лог прогона и сам проверяю, что новый тест падает без исправления.
- Каждый запуск стоит денег, поэтому бюджет на PR ограничен кодом, а повторные раунды ревью я останавливаю, когда
  остаются мелочи.

## Деплой

### Docker

`Dockerfile` в корне собирает образ, в котором один процесс отдаёт и API, и фронтенд. Приложение стартует само и
слушает порт из переменной окружения `PORT` (по умолчанию 3000):

```bash
docker build --tag calendar .
docker run --rm --env PORT=8080 --publish 8080:8080 calendar   # http://localhost:8080
```

### Render

Приложение опубликовано на [Render](https://render.com/) как Docker-сервис `call-booking` на бесплатном тарифе в
регионе Frankfurt: <https://call-booking-50q8.onrender.com>. Render собирает образ из `Dockerfile`, сам задаёт `PORT`
и выкатывает `main` этого репозитория. До переноса сервис деплоился из исходного репозитория
[`ai-for-developers-project-386`](https://github.com/sergdenisov/ai-for-developers-project-386).

### Хранение данных

Типы событий и записи лежат в памяти процесса, поэтому **после перезапуска все данные сбрасываются**: приложение
стартует с пустыми списками. Перезапуск происходит при каждом деплое, а на бесплатном тарифе Render ещё и после
простоя: сервис засыпает примерно через 15 минут без запросов, и первый запрос будит его около минуты. По этой же
причине экземпляр сервиса должен быть один: второй не увидит записи первого, и запрет пересечений перестанет работать.

### Подключение Render MCP

Агент выкатывает и проверяет сервис через [Render MCP](https://render.com/docs/mcp-server). Конфигурация для Claude
Code лежит в репозитории: `.claude/settings.json` включает официальный плагин `render@claude-plugins-official`,
который подключается к `https://mcp.render.com/mcp`. Вход идёт через OAuth, поэтому ключей в репозитории нет.

1. Откройте проект в Claude Code и подтвердите установку плагина. Если Claude Code её не предложил, выполните
   `/plugin install render@claude-plugins-official`, а затем `/reload-plugins`.
2. При первом обращении к Render агент покажет ссылку: откройте её и разрешите доступ. Данные сессии Claude Code
   хранит сам, вне репозитория.
3. Для проверки попросите агента показать список сервисов Render.

Вместо OAuth можно использовать API-ключ: создайте его в
[настройках аккаунта](https://dashboard.render.com/u/settings#api-keys), положите в переменную окружения
`RENDER_API_KEY` и подключите сервер только для себя:

```bash
claude mcp add --scope local --transport http render https://mcp.render.com/mcp \
  --header "Authorization: Bearer $RENDER_API_KEY"
```

Ключи и токены в Git не добавляем: файлы `.env` и `.env.*` исключены через `.gitignore`.

## Коммиты

Сообщения коммитов пишем по [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <описание>
```

- **Типы:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`, `revert`
- **Область** (необязательно): `backend`, `frontend`, `spec`
- **Ломающие изменения:** `!` после типа или области (`feat(spec)!: ...`) либо `BREAKING CHANGE:` в теле коммита

Примеры:

```text
feat(backend): add event types endpoint
fix(frontend): show validation error on booking form
docs: describe commit conventions
```

## Выпуск версий

Версии выпускает [release-please](https://github.com/googleapis/release-please) по сообщениям коммитов. Версия одна
на весь репозиторий: она хранится в `version.txt`, журнал изменений — в `CHANGELOG.md`. Версии в `package.json`
пакетов не меняются.

1. После каждого push в `main` workflow `release-please.yml` открывает или обновляет release PR
   `chore(main): release X.Y.Z`: в нём новая версия и записи журнала.
2. Слияние release PR создаёт тег `vX.Y.Z` и GitHub Release.

release-please открывает PR токеном Actions, поэтому в Settings → Actions → General включено «Allow GitHub Actions to
create and approve pull requests». Без него он готовит ветку и падает на создании PR; после включения неуспешный запуск
повторяют. Если проверки release PR ждут подтверждения запуска, их запускает человек.

`main` защищён правилом «main: CI must pass» (Settings → Rules): PR не смержить, пока не прошла проверка `check` из
`check.yml`, исключений ни для кого нет. Тесты Хекслета (`build`, `hexlet-check.yml`) в правило не входят: они
запускаются только на push, а release-please пушит свою ветку токеном Actions, и такой push воркфлоу не запускает, так
что release PR никогда бы не получил `build` и остался бы заблокирован. Решение о мерже остаётся за человеком.

В журнал попадают `feat`, `fix`, `perf` и `revert`, остальные типы скрыты. До `1.0.0` ломающее изменение повышает
minor-версию, а не major. Первая версия — `0.1.0` (`initial-version` в `release-please-config.json`). Настройки
лежат в `release-please-config.json` и `.release-please-manifest.json`; манифест после первого релиза ведёт
release-please, руками его не правим.

## Сценарии работы

### Владелец

1. Заходит на главную страницу, где видит 2 ссылки в заголовке страницы: "Записаться" и "Админка", а также контент
лендинга с описанием возможностей сервиса и так же кнопкой "Записаться".
2. Нажимаем на ссылку "Админка".
3. Видит уже созданные типы событий (если они есть), список предстоящих событий (с именем пользователя, его почтой,
слотом и временем создания) и кнопку "Создать тип события".
4. Нажимает на кнопку "Создать тип события".
5. Открывается форма с полями "Название" (обязательное поле), описание (необязательное поле) и длительность
(обязательное поле).
6. Заполняет их, например "Встреча"/"Короткий тип события для быстрого слота"/"15 минут" и нажимает кнопку
"Создать тип события".
7. Видит в списке новый созданный тип события и уведомление, что новый тип события успешно создан.

### Гость

1. Заходит на главную страницу, где видит 2 ссылки в заголовке страницы: "Записаться" и "Админка", а также контент
лендинга с описанием возможностей сервиса и так же кнопкой "Записаться".
2. Нажимаем на кнопку/ссылку "Записаться".
3. Видит список доступных типов событий.
4. Нажимает на один из типов событий.
5. Открывается календарь с доступным интервалом в 14 дней.
6. Нажимает на какой-либо день в календаре.
7. Открывается список доступных слотов на этот день.
8. Выбирает какой-либо слот.
9. Открывается форму, где надо указать имя и почту, а так же информацию о записи на событие (выбранную дату,
выбранное время и длительность).
10. Указывает их и нажимает на кнопку "Подтвердить запись".
11. Видит надпись "Запись подтверждена" и кнопку "Записаться еще" (которая возвращает к шагу 5).
